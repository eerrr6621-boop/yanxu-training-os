# 语义匹配第二轮测试结论

2026-09-07 · 测试与诊断，未修改生产匹配逻辑、未上线或推送 GitHub。

**结论：本地小模型能提供有用的相关性信号，但当前规则与语义的组合尚未达到可靠选师的验收要求。建议先修复下述问题，不以此前接口测试通过或简单构造案例全对作为上线依据。**

## 测试方法与范围

- 新建 16 组构造挑战案例，在模型推理前固定允许的首选和判断理由；预期候选的位置不同，合理并列时允许多个答案。未根据结果删题、改答案或调整模型/规则。
- 对照原规则、绕过专业相关性门槛后的全候选语义比较、以及实际专业相关性过滤与分档排序组合。原规则使用当前 Java 的需求组装、自动画像、人工画像优先、相关性门槛与排序方法，通过只读诊断类调用，不连接业务库。解析后的文字是构造材料，不代表上传文档解析的完整准确率。
- 这里的“语义比较”仍包含 worker 的文本标准化、否定/属性过滤和分段，不是未处理的裸模型。全候选比较只是诊断实验，产品仍只处理原规则筛选后的候选。
- 分别使用同一来源的 FP32 与 INT8，校验候选输入顺序颠倒后分数与证据保持一致；比较首选，不以无业务意义的小数差异作结论。
- 另运行 10 项指定片段保留/排除断言、50/200 位短档案规模测试、超容量拒绝测试，以及真实模型接入的隔离师资 API 回归。
- 所有材料均为构造内容，无真实客户简历、个人账号或生产数据。

## 结果

| 方法 | 16 组中的首选命中数 |
|---|---:|
| 当前原规则 | 9 |
| 全候选语义比较（FP32） | 14 |
| 全候选语义比较（INT8） | 14 |
| 当前规则＋语义组合（FP32） | 10 |
| 当前规则＋语义组合（INT8） | 10 |

这不是实际业务准确率，也不是全部返回候选的合格率或证据安全通过率。没有相关档案时应拒绝、候选是否有授课角色、每项需求是否均满足，都必须单独验收。FP32 和 INT8 在 c05 的两位允许首选间换序，业务命中统计相同；本组问题不能靠简单切换回 FP32 解决。

- 组合比原规则改善 1 组（c08），本集未观察到首选层面的新增退化；不能外推为永不退化。
- 5 组的全部预期首选（共 6 位）在专业相关性门槛处被排除：c02、c05、c13、c14、c15。
- 指定片段保留/排除断言通过 6/10，不是完整自然语言预处理准确率。
- 真实量化模型连接 Java 后，隔离师资 API 77 项再次通过。接口运行、权限、原文引用和人工修改生命周期正常，不等于业务首选总能选对。
- 开发机 Darwin arm64 上，INT8 处理 200 位短档案/400 段，清空该测试内存缓存后约 0.89 秒，峰值约 200 MiB；不是目标服务器性能保证，也不是 200 份长 PDF 简历的吞吐量。
- 201 位候选以及 200 位/600 段均明确触发容量限制；实际产品会回退规则，不会偷偷只计算部分候选。大量长简历场景的语义可用性仍需专门验证。

## 已证实的问题

### 1. 否定漏识别与误识别

- **“从未主讲银行客户投诉处理……”** 没有被排除，仍作为语义证据返回。c14 中真正有相关授课支持的候选被旧规则挡住，而明确否认主讲的候选成为唯一入选者。即使全候选语义比较首选正确，也不能据此说否定证据安全。
- **“未担任……讲师”** 同样漏过现有否定集合。
- **“在无锡……有授课经验”**、**“无障碍服务……有教学经验”** 被整段丢弃：实现仅检查前面有“无”、后面有“经验”，没有分辨地名和专业名词。
- c08 的“没有……授课经验”虽被 worker 拒绝为语义证据，但旧规则仍给它较高专业分并保留在候选列表。模型辅助排到后面不等于从源头排除了反向资历。

### 2. 相关性规则挡住了同义表达

例如 c15 的“把杂乱数字做成老板一眼明白的图”与“商业数据可视化”在语义上相符，worker 能把预期候选排第一，但原规则返回空名单，实际产品用不到这个信号。c02 的柜面反诈，以及 c05 的客诉/录音带教也有类似问题。

不能把在库状态、预算与排期等硬条件一并放开；需要重新设计的是“专业相关候选如何进入复核范围”。

### 3. 多要求没有逐项覆盖检查

c16 同时要求客户投诉课程和 Excel 实操，worker 取任一需求片段的最大相似度，偏向只覆盖一个模块的老师。原规则中正确与错误候选同为 55.8，按实际首位严格计错；加入语义后仍未把联合覆盖者排到前面。

### 4. 单看首选会掩盖证据缺口

c10 组合首选正确，是原规则保住了唯一候选；该候选实际上没有可用语义证据。c13 也不能单独证明人工画像完整生命周期，因为正确备选被原规则排除；人工画像保护依赖另行执行的真实 API 断言与源码检查。

## 建议的下一轮修复顺序（本轮未实施）

1. 统一规则与语义中的否定、授课角色和原文范围处理；明确“不具备”与“只是参训/会务”，避免把地名、无障碍服务或“不仅”等误杀。
2. 保留在库、预算与排期硬条件，改进专业相关候选召回。语义发现的新候选需有连续原文支持，不能仅凭一个相似度阈值认定资历，也不为凑满三位强推。
3. 将主题、行业、授课对象、教学方式及“必须同时满足”的条件分别核验；信息不足单独标注，不以某一个最高分片段代表全部满足。
4. 修复后保留本组为回归，再增加新的独立测试题；用经授权、脱敏、业务人员标注的真实样本验收，覆盖无合适人选与不能确定的情况。

## 复现与原始结果

- 固定案例：[challenge_cases.json](../semantic/challenge_cases.json)
- 原始结果：[INT8](../semantic/reports/challenge-int8.json) / [FP32](../semantic/reports/challenge-fp32.json)，含案例、源代码与模型散列。
- 评估器：[evaluate_challenges.py](../semantic/evaluate_challenges.py)
- 实际 Java 规则探针：[SemanticChallengeProbe.java](../scripts/SemanticChallengeProbe.java)

在仓库根目录先将当前 `src/com/training/*.java` 和诊断类编译到新的临时输出目录，依赖 `lib/h2.jar`、`lib/pdfbox-app-3.0.8.jar`、`lib/ip2region-3.3.7.jar`。然后在已有模型运行环境执行：

```bash
python semantic/evaluate_challenges.py \
  --model-dir semantic/model --cases semantic/challenge_cases.json \
  --precision int8 --java /absolute/path/to/java \
  --classpath '/absolute/path/to/test-out:lib/h2.jar:lib/pdfbox-app-3.0.8.jar' \
  --output semantic/reports/challenge-int8.json
```

换成 `--precision fp32` 和另一输出文件可复跑原精度对照。诊断报告会如实记录失败；程序正常退出表示测试运行完毕，不表示所有业务预期通过。不要把它当作布尔式发布门禁。
