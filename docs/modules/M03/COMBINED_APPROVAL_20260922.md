# 明确兼任负责人和BP的单次审批（2026-09-22）

## 本轮结果与生效边界

M03核心新增显式兼任策略：同一人已获明确负责人和BP职责时，点击“同时完成负责人和BP审批”，一次办理同时形成两项职责的批准证据。只有一个真实办理人、一条 `APPROVE_COMBINED` 事件、一次版本递增，不伪造第二人、不插入第二条自动批准。仍须由M02单独执行团队承接。

当前用户已明确北京分公司负责人和北区BP为同一人。事实引用非Git材料 `yanxu-m01/outputs/总控_BP分区及北京管理_20260922.json`；完整姓名/原ID不复制到源码、测试或本说明。确认职责不等于账号已创建、已绑定或权限已发布。实际绑定、负责机构、在岗及专用审批授权须由M01与宿主核验。普通教师账号的资料填写权限不能替代审批权限。

这是独占核心与接线契约交付。原普通流程、持久化和站内通知已由总控接入，本轮未改这些公共文件；新兼任分支须按下列清单同步接线后才可在原界面启用。没有新UI、真实账号、真实权限发布或生产操作。

## 固定规则

| 情形 | 本轮行为 |
| --- | --- |
| 不同负责人、BP | 继续负责人→BP两次显式通过，使用原baseline |
| 明确同人兼任且机构符合 | 新流程显式选用兼任策略；待办只有一个“同时完成负责人和BP审批”动作 |
| 同人但兼任依据/机构/账号未核实 | 不选择兼任策略，不按姓名、区域或相同ID自动放行 |
| 填报人也是兼任审批人 | 禁止提交为兼任流程，禁止自批，不自动指定替代人 |
| 兼任人退回 | 必填原因，退回原填报人；两项批准均未成立 |
| 退回或撤回后重提 | 原填报人重提，从兼任待审重新开始，旧内容/旧轮次证据不复用 |
| 待审内容变更 | 需新内容版本和变更说明，重新待审，清空两项批准 |
| 撤回 | 原填报人可在待审或已退回时撤回；完成两项审批后不可撤回或直接修改 |
| 代理或离岗 | 兼任仅本人办理，代理禁止；未知在岗状态提示待配置，离岗禁止办理 |
| 职责/机构变化 | 冻结历史不改；宿主重新核验当前权限及职责，不再符合时暂停办理，不静默替换人或策略 |
| 承接后回退 | 本轮不提供跨模块回退；仍由M02门禁控制 |

返回兼任待审时内部状态仍为 `LEADER_PENDING`、`stage=LEADER`；`reviewMode=SINGLE_EXPLICIT` 明确这是一个同时承担两职责的节点，不存在 `BP_PENDING` 或“第二步自动通过”。原页面状态文案应为“待负责人及BP审批（兼任）”。普通 `APPROVE` 在此模式返回 `EXPLICIT_COMBINED_REQUIRED`，避免旧界面模糊点击触发两项确认。

## 核心与快照接口

新增 `CombinedAssignment(organizationCode, approverId, directoryVersion, evidenceRef)`，四项均必填、从服务端可信配置取得。证据引用不作为权限本身，也不能来自HTTP请求体。

新流程显式创建 `Policy.combinedBaseline("M03-COMBINED-20260922-v1", assignment)`，并调用 `submit(..., access, organizationCode)` 重载，最后机构参数取M02可信单据。不带机构的旧重载不能提交兼任策略。核心验证机构匹配、负责人=BP=冻结审批人、填报人不同。策略快照固定禁自批/代理、退回填报人及从头重审。`Policy.reviewMode()` 由是否有完整兼任依据决定，不能只写一个ALLOW就变成单次审批。

原11参 `Policy` 构造器、baseline、unconfigured及旧submit签名保留；旧11参 `combinedRoles=ALLOW` 仍为顺序两次通过。旧baseline继续禁止兼任。**新策略只供新流程显式选择，现有待办/已审批快照不自动升级，不提供隐式迁移。** 即使今天人员配置发生变化，也不能回写历史策略或补造兼任事件。

`Event` 原构造签名保留。新增 `responsibilities()`：普通APPROVE按真实节点返回单项；APPROVE_COMBINED返回 `[LEADER,BP]`；其他动作为空。`view` 增加reviewMode和每条历史的responsibilities。兼任READY校验要求最后一条为同内容版本的真实兼任动作；State恢复回放还校验固定办理人、无代理、两项批准标记、节点、退回目标、重提轮次和时间/版本顺序。

新增纯工具 `ApprovalWorkflowSnapshots`：

- `encodePolicy` 保存原规则及reviewMode、combinedAssignment；必须在首次SUBMIT同一事务保存，不能审批时补写。
- `decodePolicy` 只有扩展字段**全部缺失**才按旧顺序快照读取。显式未知/空模式、依据缺项、仅有依据无模式、顺序模式夹带依据、冲突安全规则都返回INVALID_STATE；不能回退baseline或当前配置。
- `decodeEvent` 兼容旧事件没有responsibilities；有该字段时必须与规范动作一致。职责由动作唯一决定，省略该冗余字段不能把旧APPROVE升格为兼任。恶意小数版本、错误类型和时间拒绝恢复。
- 工具只服务可信持久化数据，不是请求体适配器。机构与M02、当前身份/授权与M01的核验仍属于宿主。

## 幂等、通知与催办

核心对重复requestId返回DUPLICATE_REQUEST，对旧版本/旧节点分别拒绝；兼任只增加一个版本和一条事件。宿主继续同一锁和数据库事务保存状态、审批事件、M02版本、outbox及请求结果；同账号同请求的合法重试只返回原结果，重验权限且不新增事件或重复投影。客户端超时复用原请求ID并读回状态，不能自动生成新请求再次确认。

提交/重提产生一条兼任人TODO；兼任通过直接产生一条TEAM_READY给明确团队队列，不产生给本人的第二次BP待办、不生成两条批准通知。退回通知原填报人；撤回通知填报人并取消审批人当前事项。团队承接后对原填报人的通知仍由M02真实承接事件产生。团队收件人未配置按现有S01规则BLOCKED，不猜全体管理员、不阻断有效审批。待审24小时后由填报人手动催办，同流程间隔24小时，接收人只有当前兼任人；不自动定时发送。REVISE/REMINDER的正式通知渠道仍遵守S01既有未配置边界，本轮无外发。

## 总控公共接线清单（本轮未修改）

按函数定位，行号会随总控工作变化；下列能力须一并完成后启用新模式。

| 文件/接点 | 必要变化及失败后果 |
| --- | --- |
| WorkflowIntegration.submitDemand（约130） | 保留填报人与任一审批人相同的自批拦截；负责人=BP仅在M01可信兼任依据、机构/账户/授权核验完整时选择新版本。调用带M02机构的submit。现有同人统一422需局部改动。 |
| WorkflowIntegration.applyApproval、detail（约179、232） | 将APPROVE_COMBINED归到approval.review HANDLE，不能落入demand.write。所有列表/详情可办性及动作前复核当前M01绑定、在岗、两项职责覆盖同机构；关系变化时只读历史并暂停动作。 |
| WorkflowIntegration.stateMap/loadState（约324–338） | 用encodePolicy/decodePolicy保存和恢复完整新字段，用decodeEvent核查职责；不能只保存原11字段。首次保存后立即重读也必须保留新模式，否则可能回退顺序或事务回滚。State顶层reviewMode只是展示，权威取policy。 |
| WorkflowIntegration.saveState/readiness/acceptDemand | 现有CAS、单事务和requireReadyForTeam继续使用，避免把兼任逻辑手写成两次apply；不可只凭READY字符串承接。加载时核对冻结机构与可信M02所属机构一致。 |
| NotificationChannelsIntegration.source（约197） | TEAM_READY须识别APPROVE_COMBINED→READY_FOR_TEAM，验证可信完整兼任证据；沿用BP_APPROVED业务通知时机。仍要求正常APPROVE来自BP节点。否则来源校验会409并回滚有效审批。 |
| NotificationChannelsIntegration.authority（约277） | 当前事项判断同时识别服务端启用的APPROVE_COMBINED；只查APPROVE会把兼任待办误判为已处理。历史通知/身份连续性规则保持。 |
| 原web/app.js | buildActions、workflowQueueTasks、WORKFLOW_ACTION、openWorkflowCommand识别新动作。复用原需求/今日待办/业务详情；确认文字“同时完成负责人和BP审批”，说明一次确认两项职责；历史一行展示一个办理人及“负责人、BP”两项职责，不伪造第二行/第二人。 |

M01证据须同时覆盖明确的兼任职责和需求机构。配置版本变化需要在事务锁内重新核实实际相关事实及授权，不能因为拿到了一个姓名、区域标签或“北区BP”文案便信任客户端声称的负责人身份。冻结依据始终保持原版；如事实已改变，本轮不提供沿用部分审批的人员迁移。

发布前需将新action、快照、权限、通知、原页面同轮启用；在首次写入新事件后，旧程序无法识别新action，不能直接回滚到旧二进制。未写入新流程时现有宿主仍保持普通基线，不能宣称仅换核心已开通北京兼任审批。
