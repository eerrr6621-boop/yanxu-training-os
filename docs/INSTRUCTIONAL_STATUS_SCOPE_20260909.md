# 需求中的信息状态，不等于讲师资格状态

2026-09-09。本地修复及验证记录，不是发布公告或推荐准确率报告。

## 修复内容

原始开发需求要求讲师过去给回访坐席完整教过通话纪要整理，接着描述课堂要教“如何分清已核实内容和待确认说法”。原worker在模型编码前，仅因“待确认”就抛出complex_requirement_requires_review，整条需求无法继续处理。

新增requirement_content.py，以整句语法识别明确、肯定的课程教学指令及两个信息状态名词对象，包括“已核实和待确认的信息”这种共用名词形式。仅将这类词视为课程内容，不视为讲师资料待核。原需求完整保留；不删条件、不改成主题关键词、不把内容描述当作讲师已经完成的经历。

识别不接受额外讲师谓语、计划、否定教学指令、未知对象或尾随条件。横向空白只用于识别，不连接换行/标点两侧的文字。讲师履历待确认、没有授课经历、其他人物授课等仍按原规则处理。明确排除条件仍单独保留且exclusions_enforced=false。简历证据提取和全部Java业务源码未改。

## 实际验证

- 新8项测试方法覆盖288种肯定语法组合、相近资格/否定/计划反例、跨标点和换行限制、原文保留、排除条款及worker响应边界；原50项worker测试通过。
- 首次新测试实际失败：一项误以为NFKC会消除横向空格，另一项误以为Python响应有verified字段。已保留失败记录；分别修正局部空白识别与测试的既有协议预期，没有添加响应字段迁就测试。
- 完整隔离回归实际退出0，师资产品87通过、0失败。仅使用临时本机服务和一次性数据库，不接生产。
- 使用同一原BGE INT8和同一当前Java类，改动前worker快照、改动后worker分别在独立进程重跑原30条需求，每边274份候选输入；60次真实比较调用，旧版29完成/1拒绝，新版30完成/0拒绝。不是后训练或新模型。
- 旧worker逐项复现上次候选审计和名单。除PD30外的29条，模型输出除elapsed_ms外完全相同，候选审计、准入和名单完全相同；其中包括19份真实简历×8条历史需求的152份候选审计。这是旧历史回归，不是新盲测或人工金标准准确率。
- Node核对2355处原文范围以及全部输入/权重/源码/Java类摘要。Python AST核对只有requirement_units函数变动，另98个顶层节点不变；274篇输入的原始简历证据分析与旧worker完全一致。

## 保留的真实失败与下一步

PD30由需求拒绝变为正常处理，但三份材料仍都没有可用语义证据，similarity=null，最终名单仍为空。**本次没有恢复这条需求的正确讲师推荐，不能把30/30处理完成称为100%匹配准确率。** 原PD08、PD42的业务结果也未改善。

直接读取原文和当前程序，定位到剩余问题：

1. 简历中的“学员带走的是空白纪要模板，不是客户信息”触发全段否定检查。这是课堂产物说明，不是在否认本人授课；但当前Python证据层与Java叙述层都仍拒绝这段上下文。
2. 需求“通话纪要整理”与简历课程“通话纪要的写法”没有完成同义内容与经历绑定，不能只靠一个总相似度把对象错误或同事授课反例一起放入。
3. 需求覆盖层还把“分清已核实内容和待确认说法”拆为两个培训主题，关系语义尚未完整承载。

下一项需处理“学员取得的教学材料”与“讲师自身经历”之间的否定归属，并保持本人/对象/过去完成/教学形式的限制；之后继续处理课程同义内容及比较关系。不能把整段否定保护直接关闭，也不能将待核证据直接判为合格。
